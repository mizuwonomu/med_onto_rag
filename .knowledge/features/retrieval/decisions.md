# decisions.md (why — the expensive part)

**Chosen approach + why:**

- **Union of dense ∪ BM25, no RRF/ensemble layer** (commit fc243d3, branch ner/retrieval, 2026-07-29). The reranker rescores the entire union and floor/margin then operate on reranker scores, so any fusion ordering is discarded downstream. An RRF layer would add two hyperparameters to tune without changing the candidate set. Measurement confirmed the union is what carries the value: ICD dense-only 0.814 / bm25-only 0.799 → union 0.905; RxNorm 0.865 / 0.920 → 0.965. Each branch alone loses 8–10 points against the union.

- **BM25 tokenizer = NFC + lowercase + whitespace split**, no stemmer, no stopwords, no pyvi/underthesea (commit fc243d3, branch ner/retrieval, 2026-07-29). The operative reason is *role*, not quality: the sparse branch is responsible only for recall, and whitespace matching scores partial overlaps (recall-favouring) while word segmentation demands the whole compound (precision-favouring) — precision is the reranker's job. Segmentation also has a total-failure mode: a mis-segmented `thực_quản` matches nothing when the KB stores the syllables apart. Whitespace has no such mode.

- **`sentence_transformers.CrossEncoder` for Qwen3-Reranker-0.6B** (commit fc243d3, branch ner/retrieval, 2026-07-29), not raw `transformers` (which means reimplementing the chat template and yes/no-logit scoring that ST >= 5 already provides) and not LangChain's `CrossEncoderReranker`/`ContextualCompressionRetriever` (a doc-in/doc-out compression abstraction that discards the raw scores floor/margin and the dump require).

- **Thresholds applied to document scores, codes expanded afterwards** (commit fc243d3, branch ner/retrieval, 2026-07-29). A RxNorm alias resolves to several RXCUIs; scoring at code level would duplicate one document score across many codes and destroy the meaning of margin.

- **`dense_search` is a plain function, not a `BaseRetriever`** (commit fc243d3, branch ner/retrieval, 2026-07-29). `VectorStoreRetriever._get_relevant_documents` discards scores in every branch — including `similarity_score_threshold`, which computes them and then drops them at `docs = [doc for doc, _ in docs_and_similarities]`. `dense_score` is not decoration here: it is what produces the per-branch contribution table that justified the union. The accepted cost is that dense is not a `Runnable`; when LCEL is genuinely needed, `RunnableLambda` restores that in one line, and the right unit to wrap is `retrieve_candidates`, not the individual branch. BM25 *is* a `BaseRetriever` because it owns real state (index + corpus + persistence); Chroma already owns that state, so wrapping dense would forfeit the scores for nothing. A second, architectural reason reinforces this: `as_retriever(search_type="similarity_score_threshold")` filters **before** reranking, on the dense similarity scale — a different scale from the reranker logits that floor/margin are calibrated on. Cutting there would silently discard candidates by a criterion never measured. `as_retriever` is the right tool for classic RAG, where documents feed a prompt and nobody needs the scores; this is entity linking, where the scores *are* the product.

- **`candidates_score`: `len(gold)+1` is the averaging weight, not a denominator** (commit 4f9c6cf, branch ner/retrieval, 2026-07-29). Per-candidate Jaccard is plain. Implementing it as a denominator would cap a perfect prediction at 0.5 and distort the entire optimization surface. The formula was clarified directly by the user rather than guessed.

- **Cluster-aware, stratified sweep/dev split** (commit 4f9c6cf, branch ner/retrieval, 2026-07-29). Rows sharing a `cluster_name` form one indivisible unit because a cluster's distractors are other members' gold; splitting one leaks that structure from tuning into evaluation. Stratification by `(noise, gold_kind)` is applied at unit granularity (a cluster takes its majority stratum), so the 75/25 ratio is approximate **by design** — the cluster constraint wins and stratification yields.

- **Per-KB thresholds *and* per-KB query variants** (commit 7d90952, branch ner/retrieval, 2026-07-29). ICD and RxNorm reranker scores are not on a shared scale, so one common pair always sacrifices a side — this was in the plan. What the plan did not anticipate is that the *query variant* needs splitting too: ICD wins under `raw` (bootstrap floor `[1.490, 1.890]` vs `[-0.906, 1.890]`), RxNorm under `strip_dose` (bootstrap collapses to a single point, sweep−dev = +0.0004, candidates_score 0.837 vs 0.800).

- **Raw logits, never sigmoid or softmax** (2026-07-29, discussed and settled; no code change needed). Sigmoid is monotonic so ranking and recall are unchanged, but it compresses the high-score region — ICD gold p25..p75 = 3.68..5.84 collapses to 0.975..0.997 — and floor/margin measure *differences*, so after compression the same margin admits a different number of documents depending on where top-1 falls; margin becomes non-linear in position. fp16 then quantizes away what resolution remains near 1.0. Softmax is worse: it normalizes per mention's candidate set, so an absolute floor loses all meaning. If a probability must ever be shown to a human, calibrate with Platt/isotonic on the dev split and only at the display layer.

**Assumptions it rests on:**

- The KB text (`page_content`) is the only doc-side signal fed to the reranker. ICD sibling separation is assumed achievable from the description alone — measurement suggests it is **not**, which is the open problem.
- A RxNorm alias's `resolve_in` is complete, i.e. the top-ranked alias document really does cover the full gold set. This is what makes `margin = 0` correct for RxNorm; it is a property of the KB build, not of the test set. If the RxNorm ETL's missing `rela` filter (see `tracker.md`) is corrected and `resolve_in` shrinks, `margin = 0` must be re-derived.
- Mentions arrive as single-concept strings. The whole layer is calibrated on synthetic mentions; interaction with real NER output (boundary errors, multi-concept spans) is unmeasured.
- Thresholds assume the current reranker **and** its frozen instruction. Either changing invalidates every number.
- The BM25 corpus and the Chroma index are built from the same loaders, so `doc_id` is a shared universe and union is a plain set-union. Any future branch built from different loaders silently degrades the union into a concatenation.
- The synthetic set is representative of the organizer's test distribution. It is LLM-generated and cannot cover the full space — accepted deliberately after weighing more generation against its collision rate.

**Failed approaches:**

- Tried: gate rule "every distractor must be some other row's gold in the same cluster" — Failed because: it produced 48 false errors across 8 valid clusters. A cluster legitimately contains sibling codes that only ever act as noise (e.g. `ICD_AminoAcid_UreaCycle`: gold spans E72.2/E72.3, while E72.4/E72.5 exist purely as distractors). A gate that cries wolf at scale is more dangerous than a loose one, because users learn to skip its output and real errors ride along — Avoid when: tempted to define hard-negative validity by role-symmetry between rows. Use *region* membership instead (same ICD block / same `resolve_in` group). **Cross-cutting**: the same reasoning applies to any future data gate.

- Tried: measuring the margin floor as the score spread between gold **documents** — Failed because: it reported RxNorm as needing margin ≈ 5.16 when it actually needs 0. One alias document expands to the whole gold code set, so the requirement must be measured over expanded **codes**. The wrong measure produced a spurious "no margin can satisfy every row" verdict for RxNorm — Avoid when: any metric asks "how far apart are the correct items"; ask instead "how far down must we go before the *union of what we produce* covers the target."

- Tried: `data/test/rxnorm_icd_synthetic_400-v2.jsonl` as the calibration set, as named in the original plan — Failed because: that file only carries `{mention, kb, gold, noise}`; the `distractor`, `cluster_name` and `gold_kind` fields the entire plan depends on live only in the `-labeled` variants — Avoid when: a plan names a data file; verify its schema before building on it.

- Tried: calibrating on the synthetic set as delivered, without deduplication — Failed because: 94 of 400 rows were exact duplicates, concentrated in `noise=heavy` (56% of heavy rows collided vs 11% of mild). The weakest reported number (heavy recall 0.771) was partly an artifact of a few bad mentions counted repeatedly; on a clean set it rose to 0.850 — Avoid when: any LLM-generated set is used for measurement. Generation collapses hardest exactly where the noise is strongest.

- Tried: 10 large clusters per KB — Failed because: clusters are indivisible split units, so 10 clusters means dev receives 2–3 units and the bootstrap floor spread covers nearly the whole axis (`[0.014, 3.807]`). Raising this to 50 clusters of 6 rows collapsed it to `[1.490, 1.890]` with the same algorithm and the same seed — Avoid when: tempted to fix split instability by adding rows. **Unit count is the governing variable, not row count.**

- Tried: distractors drawn from a broad concept group rather than from the cluster's own sibling set (synthetic v2) — Failed because: 237 rows carried distractors belonging to no member of their cluster, which inflates the measured margin ceiling (the gap is computed against an irrelevant code) and renders the distractor-leak report meaningless — Avoid when: generating hard negatives topically. Draw them from the same sibling group the golds come from.

**Nuances agreed with the user:**

- Two rounds of measurement, on different data (one of which had 21 structurally wrong `multi_solving` golds), converged on RxNorm `margin = 0` and floor 2.021 → 2.157. That convergence, **plus a structural explanation**, is what justified freezing RxNorm while leaving ICD tentative. Reproducibility across independent measurements was treated as stronger evidence than any single run's confidence interval.
- The apparent "reranker scores distractors very highly" in the histograms was investigated and rejected: `density=True` normalizes each group separately, so distractor and gold densities are not comparable. Head counts show the right tail is nearly pure gold (ICD ≥ 6.0: 36 gold vs 3 distractor; RxNorm ≥ 4.3: 40 vs 1). The real overlap is **mid-scale**, where ICD distractor p75 (3.477) exceeds gold p25 (3.156).
- ICD's remaining weakness was explicitly diagnosed as a **reranker capacity limit, not a data-volume problem**, and the user was advised against generating more synthetic data to fix it.
- Dropping the `N00.0` row was correct and does not indicate a KB gap: the KB holds 9073 four-character codes and `N00` legitimately has no listed children (ICD-10 shares the `.0–.9` morphology table across N00–N08). The generator should nonetheless draw gold **from `icd_concepts.jsonl`** rather than from general ICD-10 knowledge, since the KB is a list of explicitly enumerated codes, not the full valid ICD-10 space.
- The claim that Vietnamese segmenters are "brittle on medical terminology" was an **untested assumption** written into the first docstring, and was challenged by the user. It has been softened. The honest position is that whitespace suits the branch's recall-only role; a hybrid tokenizer (indexing both `[viêm, cầu, thận]` and `viêm_cầu_thận`) is additive, cheap, and worth trying — but after the reranker bottleneck, not before.

# decisions.md (why — the expensive part)

**Chosen approach + why:** Keyed candidate docs by RXCUI rather than RXAUI (commit 66b0d38, branch build_kb (removed), 2026-07-08) because every downstream join operates at concept level, RXNREL links via `rxcui1`/`rxcui2`, and gold evaluation labels are RXCUIs. RXAUI is an atom-level identifier; using it as the candidate key would silently produce codes from the wrong identifier namespace, scoring zero without raising any error.
- Assigned RXNREL as the sole source of the resolved code and demoted RXNCONSO to a gatekeeper via `EXISTS` (commit XXX, branch XXX, XXX). `r.rxcui2` _is_ the code to export; joining back to RXNCONSO is only to confirm that RXCUI has a valid `TTY IN ('IN','MIN')` atom with `suppress='N'`. Separating "source of data" from "filter condition" was what surfaced the RXAUI bug in the first place.
-  Stored `resolve_in` and `resolve_min` as two parallel fields inside a single JSONL record rather than two files (commit XXX, branch XXX, XXX), so the two mappings cannot drift out of sync. The IN-vs-MIN choice is deferred to index-build time via a config key (`combination_resolve: "in" | "min"` in `configs/kb.yaml`), with only one `resolve_to` reaching the LangChain `Document`. Flipping the strategy costs a config edit plus an index rebuild, never a KB rebuild.
-  Brand docs retain both `suppress='N'` and `suppress='O'`, while resolve targets are hard-filtered to `suppress='N'` (commit XXX, branch XXX, XXX). Real prescriptions cite discontinued brand names, so those must remain _findable_; but what they resolve _to_ must always be a currently active generic.

**Assumptions it rests on:**
    - Gold labels are RXCUIs, not RXAUIs. If the evaluation switches to atom-level codes, the entire candidate keying is wrong.
    - Brand-to-generic traversal is a single hop, `rxcui1 → rxcui2` in RXNREL. Any brand reachable only via a multi-hop path (e.g. through an SCD/SBD intermediate) is silently absent from the export.
    - The RxNorm release is treated as static; the KB is a snapshot with no update path. `rela` vocabulary is version-dependent, so any hardcoded `rela` filter added later must be re-verified against the new release.
    - `sab='RXNORM'` is sufficient to exclude source-vocabulary noise (MTHSPL, VANDF, etc.) from both candidates and resolution targets.

**Failed approaches:**
    - Tried: `COPY ... WITH (FORMAT text, ..., QUOTE E'\x01')` → Failed because: `QUOTE` is rejected outside CSV mode (`SQL Error [0A000]`); `text` format has no quoting concept at all → Avoid when: porting a MySQL `LOAD DATA` statement and assuming its options map one-to-one onto `COPY`.
    - Tried: `FORMAT text` for loading the RRF files → Failed because: `text` mode hardcodes `\` as its escape character and offers no way to disable it, so rows whose `STR` ends in a backslash (e.g. `...CONE,SZ 18\|`) swallow the following delimiter and fail with `missing data for column "fk"` → Avoid when: the source format has no escaping convention of its own. The working port of MySQL's `ESCAPED BY '<rare char>'` idiom is `FORMAT csv` with both `QUOTE` and `ESCAPE` set to `E'\x01'`, since only CSV mode exposes an `ESCAPE` option.
    - Tried: loading RRF with a column list matching the table's 18 columns → Failed because: every RRF line has a trailing `|`, producing a phantom 19th empty field; MySQL tolerates this, PostgreSQL raises `extra data after last expected column` → Avoid when: assuming a delimiter-terminated format is delimiter-_separated_. Resolved by `ALTER TABLE ... ADD COLUMN fk` before `COPY` and `DROP COLUMN fk` after, leaving both the raw file and the final schema untouched.
    - Tried: `resolve_in` / `resolve_min` populated from `g.rxaui` of the gatekeeping RXNCONSO join → Failed because: this exported atom identifiers where concept identifiers were required, mixing namespaces without any error → Avoid when: a join is present for validation and its columns are within easy reach; the temptation is to read the code off the joined table instead of the table that actually owns it.
    - Tried: flattening brand names into the `synonyms` field of generic candidate docs → Failed because: a brand may contain several ingredients (Vicodin → acetaminophen + hydrocodone), so folding it into one ingredient's synonyms loses the others, while a single ingredient appears across hundreds of brands, inflating the field and destroying the 1:1 precision needed to return a correct RXCUI → Avoid when: tempted to precompute cross-concept relations into intra-concept fields. Cross-RXCUI mapping belongs in the alias doc's `resolve_*` fields.
    - (Cross-cutting, promote a pointer to `index.md`: the RXAUI-vs-RXCUI namespace failure, and the CSV-mode escape workaround, since both govern any future reload or re-export.)

**Nuances agreed with the user:**
    - Alias docs stay keyed by RXAUI (`b_<rxaui>`) even though their payload is RXCUI-based. Brand strings vary per atom and that granularity is wanted for retrieval recall; only the _resolution target_ must be a concept code. A consequence not yet measured: one brand concept can emit several `b_` docs.
    - Multi-ingredient brands intentionally resolve to a list, not a single winner. With no gold candidate set available, returning all constituent ingredients is preferred over an arbitrary collapse.
    - `SY`/`TMSY` atoms are demoted to `synonyms` of their own RXCUI rather than promoted to standalone candidates. `BPCK`/`GPCK` (packaging) and `DF`/`DFG` (bare dose form, e.g. "Oral Tablet") are excluded outright as meaningless retrieval targets.
    - Export uses `COPY (...) TO '<path>' (FORMAT text)` rather than DBeaver's export UI: its JSON writer nests the record as an escaped string, and its CSV writer wraps and doubles quotes, both corrupting JSONL.

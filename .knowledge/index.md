# index.md (current architecture — structural, durable)

## ICD-10 parser
The ICD-10 feature parses the bilingual two-column `data/raw/ICD_10.pdf` (English left, Vietnamese right, ~841 pages) into `data/processed/icd_concepts.jsonl`, one flat record per ICD code, serving as Entity-Linking candidates for the CHAN_DOAN branch. It is split into: `src/kb/icd.py` (page column detection + code-anchored parsing + EN/VI join + record building), `src/kb/icd_hierarchy.py` (static range→chapter/block table), `src/kb/icd_text.py` (head/tail name-vs-note splitter), `src/configs/config.py` (tuning constants), and `scripts/build_kb/icd/build_icd_kb.py` (entrypoint). The defining boundary: the **ICD code is the anchor**; the two language columns are parsed independently into `{code → description}` streams and joined **by code**, never by geometric row/position — so page breaks and EN/VI line drift are harmless.

- **Cross-cutting:** the flat JSONL record schema (`text`, `name_vi`, `name_en`, `note_vi`, `note_en`, `code`, `chapter`, `block`, `kb`, `role`, `vi_glyph_ok`) is meant to be shared with other KB branches (RxNorm etc.). `text` is the sole field sent to embedding + BM25. Changing this shape forces re-ingestion — warrants a pointer line at the top of `index.md`.

## RxNORM parser
The RxNorm ETL layer introduces a two-document-type knowledge base exported directly from PostgreSQL as JSONL. Type one is the **candidate doc** (`c_<rxcui>`), representing an active generic ingredient: it carries `text` (the ingredient's preferred string), `code` (RXCUI), `role: "candidate"`, and a `synonyms` list gathered from same-RXCUI atoms. Type two is the **alias doc** (`b_<rxaui>`), representing a brand-name atom: it carries `text` (brand string), `role: "alias"`, and two parallel resolution fields, `resolve_in` and `resolve_min`, each a list of generic RXCUIs. Traversal from brand to generic is fully precomputed at build time via RXNREL, so runtime retrieval reads metadata only and never joins. Three SQL files constitute the layer: `export_candidate_jsonl.sql`, `export_brand_jsonl.sql`, and `trace_resolve_brand.sql` (a manual inspection query, not part of the build).

- **Cross-cutting (CONCEPT GRANULARITY - the contract that was wrong):** the export selects **ingredient-level** concepts only (`tty='IN'`), so `chlorpheniramine` is `2400`. The organizer scores mostly against **`SCD`** - ingredient + strength + dose form, `amlodipine 10 MG Oral Tablet` = `308135` - which is **absent from the exported KB entirely**. No retrieval, reranking or threshold change can reach a code that is not in the index, so every drug link is structurally incapable of scoring until the export is widened. Gold is **mixed**, not uniformly one level: `nystatin` = `7597` is a bare `IN`, so the export must carry `IN` and `SCD` together and let retrieval choose. The granularity of the export - not just the identifier space - is part of the contract, and it must be chosen against the *consumer's* gold, never against convenience. Measured 2026-08-03 over the 13 gold RXCUIs in the organizer's examples; the earlier `SCDC` hypothesis was refuted by that same query.
- **Cross-cutting (granularity and thresholds are one decision, not two):** widening the export changes what the calibrated retrieval settings mean. `strip_dose` was safe while every concept was ingredient-level and destroys the only distinguishing field once strength-level concepts exist (`clonazepam 0.5 MG` vs `1 MG`); `margin = 0` rested on one alias expanding to the full RXCUI set, which stops holding when a drug has dozens of strength siblings. Any change to KB granularity must be measured together with the query variant and thresholds of the branch it touches - never shipped as an index rebuild alone.
- **Cross-cutting (only `page_content` is searchable):** `load_documents` routes everything except `text` into metadata, and both index branches are built from `page_content`, so a field that lives in metadata is stored but never matched. `synonyms` is in that position today: exported by SQL, serialized by the loader, read by nothing. Adding vocabulary to a KB record only helps if it reaches `page_content` or an index built from more than it - and the two branches want different things there, since extra surface forms help BM25 while blurring a dense vector.

This is **cross-cutting**: it defines the identifier contract (RXCUI at concept level) shared by the retrieval index, the downstream entity-linking evaluation, and any future KB rebuild. A pointer line at the top of `index.md` is warranted.

## Vector index
The vector-index layer (`src/index/`) is the first stage of retrieval: it loads the three processed KB JSONL files into LangChain `Document`s and embeds them into two on-disk Chroma indexes, `data/index/icd_db` (collection `icd`) and `data/index/rxnorm_db` (collection `rxnorm`), both cosine space, ids = `doc_id`. It splits into `index/load_documents.py` (JSONL → `Document`: NFC-normalize `text` into `page_content`, route the rest into scalar-only metadata, skip/dedup invalid records), `index/ingestion.py` (`ingest_collection()` — a generic, embedding-agnostic writer that wipes and rebuilds a collection in batches), and `index/build_vector.py` (the `python -m index.build_vector` entrypoint that wires the model and orchestrates both collections). The defining boundary: **"how to write vectors" (ingestion, model-agnostic) is separated from "which model produces them" (build_vector)**, so the embedding model can be swapped or a BM25/hybrid stage added without touching the writer.

- **Cross-cutting (embedding + storage contract):** the embedding model (`Qwen/Qwen3-Embedding-0.6B`), normalization, cosine space, and the **asymmetric** query-vs-document encoding (query gets `prompt_name="query"`, document side plain) form a frozen contract — changing any of them invalidates every stored vector and forces a full re-ingestion. Equally frozen is the metadata shape: Chroma accepts scalars only, so list fields (`synonyms`, `resolve_in`, `resolve_min`) are stored as JSON strings and the retrieval side must `json.loads` them, never substring-match the raw value. Both warrant a pointer at the top of `index.md`.
- **Cross-cutting (in-process rebuild):** chromadb caches its `PersistentClient` per `persist_directory` at the process level, so any code that deletes and recreates a persist dir within one process must call `SharedSystemClient.clear_system_cache()` after the wipe, or the stale cached client fails with `attempt to write a readonly database`.
## Retrieval layer
The retrieval layer (`src/retrieval/`) sits between the vector index and the future NER pipeline: given a mention string and a KB name, it returns a set of codes. It splits into a **sparse branch** (`bm25_retriever.py` — `BM25SRetriever`, a `BaseRetriever` wrapping `bm25s`, persisted to `data/index/bm25_{icd,rxnorm}` with a sidecar `documents.jsonl` carrying doc_id + metadata), a **dense branch** (`dense_retriever.py` — a read-only opener over the existing Chroma stores plus `dense_search`, deliberately a plain function rather than a `BaseRetriever`), a **cross-encoder** (`reranker.py` — `Qwen3Reranker` over `sentence_transformers.CrossEncoder` with a frozen task instruction), and the **per-mention pipeline** (`hybrid.py` — `retrieve_candidates` → `rerank` → `apply_thresholds` → `expand_codes`). A parallel set of evaluation primitives (`metrics.py` for the organizer's `candidates_score`, `query_variants.py`, `splits.py`) exists to calibrate that pipeline rather than to serve it, and `scripts/retrieval/` holds the measurement entrypoints (`validate_synthetic` → `build_bm25` → `dump_scores` → `analyze_distribution` → `sweep_thresholds`). The defining boundary: **both branches are responsible only for recall@union; all filtering is deferred until after reranking**, so no score threshold is ever applied on a scale other than the one floor/margin were calibrated on.

- **Cross-cutting (score-scale contract):** floor/margin operate on **raw reranker logits**, and the reranker's task instruction is part of that scale. Changing the reranker model, its instruction, or applying sigmoid/softmax invalidates every calibrated threshold — sigmoid compresses the high-score region so the same margin admits a different number of docs depending on where top-1 falls; softmax normalizes per candidate set so an absolute floor loses all meaning. Thresholds live in `configs.config.RETRIEVAL_THRESHOLDS`, stored per KB **together with the query variant they were measured under**. Equally part of the contract is the **measurement scope**: every number was calibrated on 399 LLM-generated synthetic rows and has never seen a real clinical note or real NER output, so the thresholds are a grounded starting point rather than accepted values. Note the asymmetry this creates — RxNorm's `margin = 0` is backed by a *structural* fact (one alias document expands to the full RXCUI set via `resolve_in`, so rank-1 already covers the gold), which the synthetic set merely confirmed; ICD's pair has no such backing and rests on the data alone. Warrants a pointer at the top of `index.md`.
- **Cross-cutting (doc_id universe):** the BM25 corpus is built from the *same* loaders as the Chroma index (`load_icd_documents` / `load_rxnorm_documents`), which is what makes hybrid union a plain set-union over `doc_id` with no mapping layer. Any future retrieval branch must be built from those same loaders or the union silently degrades into a concatenation.
- **Cross-cutting (per-KB, not global):** ICD and RxNorm reranker scores are not on a shared scale, and measurement showed each KB wins under a *different* query variant (ICD `raw`, RxNorm `strip_dose`). Any code applying one global threshold or one global query normalization is wrong by construction.

## NER extraction layer
The extraction layer (`src/extract/` + `src/pipeline.py`) is the first consumer of every layer below it: given a free-form Vietnamese clinical note, it returns the organizer's submission records. It splits into a **generation stage** (`schema.py` — the Pydantic model that is the single source of the decoding grammar; `prompt.py` — English rules plus Vietnamese few-shot; `llm.py` — a `ChatOpenAI` client pointed at a self-hosted llama-server, plus `preflight()`), an **alignment stage** (`align.py` — pure string code, no model dependency), and a **linking stage** (`linker.py` — type-based routing into the existing retrieval pipeline). `pipeline.extract_document` orchestrates one document and lives at the root of `src/` rather than inside `extract/`, because a module importing both `extract` and `retrieval` belongs to neither. The defining boundary: **the LLM generates only `text`/`type`/`assertions`** — never positions (string matching is deterministic and cheaper) and never codes (codes must be anchored in the KB through retrieval, not recalled from model weights).

- **Cross-cutting (verbatim contract):** `align_positions` overwrites `text` with `raw_input[start:end]` after locating the span, so `text` and `position` cannot contradict each other by construction rather than by discipline. The consequence propagates upward: the model must reproduce spans character-for-character *including* spelling errors, doubled spaces and odd capitalization, because a mention not found in the source is dropped entirely — losing both the mention and its candidates. The fuzzy fallback only repairs deterministic differences (NFC composition, case folding); it deliberately refuses edit-distance matching, since a wrong-but-plausible alignment fabricates a mention with a valid position, which scores worse than a clean miss. Any future component that normalizes the raw input before extraction breaks this contract.
- **Cross-cutting (output field shape):** `assertions` and `candidates` are **absent**, not empty, on types that cannot carry them — `assertions` only on `CHẨN_ĐOÁN`/`THUỐC`/`TRIỆU_CHỨNG`, `candidates` only on `CHẨN_ĐOÁN`/`THUỐC`. An empty list asserts "checked, none found"; a missing key asserts "this type does not carry the concept." The organizer reads the second meaning. The two sets are independent, so `TRIỆU_CHỨNG` carries assertions but no candidates.
- **Cross-cutting (a dropped mention is a triple loss):** `align_positions` discards any mention it cannot locate verbatim. That is not a partial penalty - the record disappears from the submission, taking `text`, `assertions` and `candidates` with it, and it also becomes a missed gold. A document that lost five concepts is indistinguishable from one that only had fifteen, which is why the drop is now reported at WARNING level rather than DEBUG. The fold repairs NFC composition and case only: it fixes how a diacritic is *encoded*, never a difference *between* diacritics (`suyễn` vs `suyến` is dropped), and never a missing letter or a missing space.
- **Cross-cutting (type drives retrieval):** `linker.TYPE_TO_KB` routes by entity type alone, so a type error is not a local scoring loss — it changes which knowledge base is queried, or whether one is queried at all. A symptom mislabelled as a diagnosis produces plausible-looking ICD candidates that no threshold can reject, because the thresholds were calibrated on genuine diagnosis mentions.
